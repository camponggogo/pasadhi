Abstract

An office of 100–200 machines already owns the capacity it rents from the cloud, but not the ability to use it as one computer. PASADHI is a matrix-first pool: one tiled kernel serves GEMM, int8 GEMM, FFT and convolution; five process layers (transport, policy, scheduler, kernel, storage) each own a bounded queue; a node plane separated from the gateway absorbs heartbeats; a content-addressed prefix cache shortens the median; and contributors are paid by measured impact rather than core-hours.

On a 50-machine test bed (8 vCPU host, Docker Desktop, mock backend) the pool serves 15.7 req/s from one gateway worker, 22.3–24.8 req/s from two, and degrades past four; 96.5 % of response time at 50 clients is queueing above a 174 ms service floor; a prefix cache takes an 8 000-token document from 111.4 s to 0.71 s (157×, 88.2 % reuse); a document router reaches 90.15 % at 31.5 µs; separating the node plane raises heartbeat capacity from 44 to 161 req/s per shard. Modelled fleets: 1 000 GTX 1050 cards give 1.30 PFLOPS f32 independent but only 0.16 PFLOPS sharded over 1 GbE (8.5 %); 1 450 mixed cards give 9.54 PFLOPS f32 and 47.7 POPS int8 in 143.5 kW; used hardware costs ฿0.016/TFLOP against ฿0.028 for cloud CPU and ฿0.001 for a rented A100; the token economy clears 68.1 % gross margin at fleet scale and 43.5 % under a 720-hour stress case.

1. Introduction

Cloud GPUs are rented by the hour and billed per token. Offices own machines that idle sixteen hours a day. The naive arithmetic — sum the RAM, sum the FLOPs — fails for a reason unrelated to silicon: coordination cost. Every added machine adds a heartbeat, a cache entry, a placement decision and a queue. Past a threshold the pool spends more time deciding than computing, and throughput stops responding to capacity.

This paper does four things. It states the coordination problem in queueing terms (§2) and derives the three ceilings that decide architecture. It describes the system (§4) and its installation (§5). It reports the measurement programme (§7) with every figure. It closes with the price model, the threats to validity and the roadmap.

2. Problem statement and theory

2.1 Notation

λ      arrival rate (req/s)          S     mean service time
W      mean time in system           Q     mean queueing time, W = S + Q
m      parallel servers              ρ     utilisation = λ·S/m
η      efficiency = S/(S+Q)          n     fleet size

Little's law fixes L = λW; the useful fraction of the pool is η. When ρ < 0.7 the pool is compute-bound and more or faster servers help. When ρ → 1 the pool is coordination-bound: each new server adds control traffic and queueing faster than it adds throughput. A 50-machine run measured η = 3.5 % at C=50 (96.5 % queueing) — the second regime.

2.2 The three ceilings

  1. Loop ceiling. One event loop serves 58.7–71.2 req/s of trivial work; a completion costs ≈60 ms of loop time.
  2. Accept-queue ceiling. Workers on one port share one queue; separate ports each own one. 2 ports beat 2 workers by 16 %, and a userspace proxy gives the gain back (−25 %) because it re-serialises accepts.
  3. Link ceiling. A sharded GEMM exchanges O(n·b²) activations per step against O(n·b³) compute, so the compute fraction falls as b/(b + RTT·BW): 6.9 % over fibre, 32.3 % over LEO, 0.004 % over Earth–Mars.

3. Design principles

  1. Matrix-first. Work is a matrix operation, not a model layer, so one kernel and one scheduler serve many workloads.
  2. Process-per-layer, bounded queues. Back-pressure is the scheduling signal; no layer can stall another.
  3. Separate planes. Gateway (requests) and node plane (heartbeats) are different processes; the node list is cached 5 s, heartbeats every 10 s.
  4. Keep the inner loop local. Tiles that fit a host stay on the host; only panel boundaries cross the wire.
  5. Price by impact. Weights come from the same sweep that produced the performance numbers.

4. Architecture

Figure 1. The full system on one floor, isometric. Devices feed the pool platform; the gateway platform holds identity, policy and audit; the app platform is the user surface; storage keeps content-addressed blocks. Red tags are measured shares: 30 % typical contribution, 88.7 % prefix hits, 96.5 % queueing at C=50, 98 % CPU weight, 42 % GPU weight.

 L5 storage     content-addressed blocks, local disks
 L4 kernel      GEMM · int8 GEMM · FFT/conv as GEMM
 L3 scheduler   tiling, placement, back-pressure, retries
 L2 policy      identity, scopes, budgets, audit
 L1 transport   framed TCP; shared memory on the same host

The scheduler keeps a placement table of (tile, host, deadline). A tile is retried if its host misses a heartbeat by more than two intervals; the retry reuses the same seed, so results are deterministic. Policy decisions (quota, scope, budget) are made once per request, not per tile.

6. Methodology

  • Host: 8 vCPU, Docker Desktop, Python 3.11, mock inference backend (fixed 60 ms service) unless stated.
  • Load: closed-loop clients at concurrency C ∈ {1, 8, 16, 32, 50, 64, 100}, 60 s per point, 3 repeats.
  • Metrics: req/s, p50/p95/p99, error rate, RSS per worker, CPU per container.
  • Fleet and price models: parameterised by measured per-card throughput and published specifications; marked as models in the captions.
  • Reproduction: every figure has a script under scripts/ or report/*/, and its numbers are recorded in report/IMAGE_FACTS*.md.

Cloud A100 reference ฿0.001 per delivered TFLOP
Credit issued 2.5 ฿/node-hour 10 % reserve

Contributors are paid in credits at 2.5 THB per node-hour, capped by a 10 % reserve. A group that shares 30 % of 150 machines earns 53 460 THB against a 149 745 THB subscription, so the honest advice is: share ≈60 %, or price the group at ≈350 THB per machine.

9. Threats to validity

  1. One host. All measured numbers come from 8 vCPU and Docker Desktop; absolute ceilings move with the host.
  2. Mock backend. Service time is fixed at 60 ms, so generation cost is modelled rather than observed.
  3. Models labelled as models. Fleet, price, orbit and token figures are parameterised by measured per-unit throughput; they are not deployments.
  4. Windows networking. --net=host is unavailable, so some port and proxy results are conservative.
  5. Two cache runs. 88.2 % reuse (text) and 88.7 % hit (figure) come from different runs of the same workload.

10. Conclusion

The pool is not limited by silicon but by coordination. Three ceilings — loop, accept queue, link — explain every result in this paper, and each has a design response: separate planes, process-owned queues, and a local inner loop. The commercial model follows the same discipline: pay for measured impact, publish the reserve, and do not claim cheaper FLOPs than a GPU. What remains is engineering: a packed int8 kernel, a shared-memory transport, a group controller, and a public network with redundant execution and spot checks.
