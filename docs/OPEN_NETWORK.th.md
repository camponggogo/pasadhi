# PASADHI แบบเปิดสาธารณะ — ตั้งแต่ Earth fibre ถึงดาวอังคาร

**ฉบับออกแบบ · 2026-10-22** · โมเดล: `pasadhi/core/orbit.py` · ผล: `bench/results/orbit_model.json`

> หลักคิดเดียวที่ตัดสินทุกอย่างในเอกสารนี้: **วงใน (inner loop) ต้องอยู่ใกล้กันเสมอ**
> สิ่งที่ข้ามดาวได้คืองานที่ไม่ต้องรอผลกลางทาง (independent job, checkpointed tile)

---

## 1. เปิดให้คนทั้งโลกเข้าร่วม — แต่ต้องตรวจงานได้

| กลไก | ออกแบบ | ต้นทุน |
|---|---|---|
| เข้าร่วม | ไม่ต้องอนุญาต (permissionless) แต่ต้องผ่าน burn-in test 30 นาที | เวลาเครื่อง |
| ตรวจผลงาน | **redundant execution 2×** + spot-check สุ่ม 5 % | ครึ่งหนึ่งของ throughput |
| กัน Sybil | credit ต้องมาจากงานที่ส่งมอบจริง (tile id + checksum), มี reputational score | — |
| กันโกง | ผลไม่ตรง → slash credit ที่วางไว้ + ตัดสิทธิ์ | เครดิต |
| ความเป็นส่วนตัว | tile เข้ารหัสฝั่งผู้ขอ, worker เห็นเฉพาะ ciphertext + โค้ด kernel | CPU เล็กน้อย |
| เงิน | credit เป็นหน่วยบัญชีภายใน; การแลกเป็นเงินต้องผ่านผู้ให้บริการที่ได้รับอนุญาต | กฎหมายแต่ละประเทศ |

**ผลที่ต้องยอมรับ:** redundancy 2× ทำให้ capacity ที่ขายได้เหลือครึ่งเดียว — ต้องคิดในราคา ไม่ใช่คิดทีหลัง

## 2. ฟิสิกส์: ความหน่วงกำหนดว่างานไหนทำได้

| ลิงก์ | RTT | GEMM 4096³ ข้ามลิงก์ | งาน batch 10 นาที | งานสั้นสุดที่ยังคุ้ม 90 % |
|---|---:|---:|---:|---:|
| Earth fibre (ตรงข้ามโลก) | 196 ms | **6.9 %** | 100 % | 2 s |
| LEO satellite (550 km) | 31 ms | **32.3 %** | 100 % | < 1 s |
| GEO satellite | 518 ms | 2.8 % | 99.9 % | 5 s |
| Earth–Moon | 2.56 s | 0.57 % | 99.6 % | 23 s |
| Earth–Mars (ใกล้สุด) | 6 min | 0.004 % | 62 % | 55 min |
| Earth–Mars (ไกลสุด) | 44.6 min | 0.0005 % | 18 % | 6.7 h |

![fig05](bench/results/fig05_orbit.png)

**อ่านตารางนี้ให้ถูก:** GEMM ที่ต้อง all-reduce 10 รอบจะเหลือ **6.9 %** แม้บน fibre ตรงข้ามโลก
(เพราะ 10 × 196 ms = 2 s เทียบกับ compute 0.1 s) — นี่คือเหตุผลที่ **การ shard โมเดล/เมทริกซ์ต้องอยู่ใน DC เดียวกัน**
ส่วนงาน batch 10 นาทีทน RTT ได้ถึงระดับดวงจันทร์ และเริ่มพังที่ดาวอังคาร

## 3. กติกาการวางงาน 4 ชั้น

```
L0  same host / same rack      → sharded GEMM, all-reduce, KV cache migration
L1  same metro (< 2 ms)        → distributed GEMM ทั่วไป, model parallelism
L2  same planet (< 200 ms)     → independent jobs, batch, cache warm-up
L3  interplanetary (min–hours) → store-and-forward เท่านั้น: ส่งงานไป, รอผลกลับ
```

**ห้ามฝ่าฝืน:** งานที่มี inner loop ต้องอยู่ L0–L1; งานที่ข้าม L3 ต้องเป็นงานที่ **ไม่ต้องรอผลกลางทาง**

## 4. Store-and-forward (DTN) สำหรับดวงจันทร์/ดาวอังคาร

- ใช้ Bundle Protocol (RFC 5050) แนวคิดเดียวกับ DTN ของ NASA: เก็บไว้ ส่งต่อเมื่อมีลิงก์
- งานถูกตัดเป็น **tile ที่ checkpoint ได้**;ดาวอังคาร worker ทำเสร็จแล้วเก็บผลไว้ รอ window สื่อสาร
- scheduler ไม่จัดงานตาม RTT แต่จัดตาม **deadline** (“เสร็จก่อน 06:00 ของวันถัดไป”)
- ผลลัพธ์ต้องมี checksum + ลายเซ็น เพื่อตรวจได้แม้มาถึงช้ากว่ากำหนด

## 5. เกิดอะไรกับธุรกิจเมื่อเปิดสาธารณะ

| ประเด็น | ก่อน (องค์กรปิด) | หลัง (public) |
|---|---|---|
| ราคา | กำหนดเองได้ | ถูกกดด้วยตลาด — ต้องขาย SLA/ความน่าเชื่อถือ ไม่ใช่ราคา FLOP |
| กำไร | margin 68 % (โมเดล 1,450 เครื่อง) | ลดลง เพราะ redundancy 2× + การแข่งขัน |
| ความต้องการ | ลูกค้าองค์กร | เพิ่มงาน batch ขนาดใหญ่, งานวิจัย, ดาราศาสตร์, การศึกษาที่ต้องการ compute ราคาถูก |
| ความเสี่ยง | ลูกค้าหนึ่งรายเลิก | Sybil, การโกงผล, กฎหมายข้ามประเทศ, ภาษี |

**จุดที่ยังชนะได้:** งานที่ต้อง **อยู่ในประเทศ** (PDPA/ข้อมูลอ่อนไหว), งานที่ต้อง **SLA เฉพาะ**, และงานที่
cloud ไม่รับเพราะสั้น/เล็ก/แปลก — ไม่ใช่การแข่งราคาต่อ FLOP กับ GPU ใหม่

## 6. แผนที่ต้องทำ (ต่อจาก M5)

**M6 — public testnet (ปี 2027):**
- [ ] node identity + burn-in attestation
- [ ] redundant execution 2× + spot-check 5 %, slash credit
- [ ] credit ledger ที่ตรวจสอบได้ (append-only, Merkle root รายวัน)
- [ ] วัด: % งานที่ถูกตรวจพบว่าโกง, ต้นทุน redundancy จริง, throughput ที่ขายได้

**M7 — orbital (ปี 2028+):**
- [ ] DTN transport (bundle) + tile checkpoint
- [ ] deadline-based scheduling แทน RTT-based
- [ ] ทดสอบกับ LEO จริง 1 ลิงก์ ( latency ~30 ms) ก่อนขยาย
- [ ] ข้อกำหนดทางกฎหมาย: การส่งข้อมูลออกนอกประเทศ, การใช้คลื่นความถี่, สัญญาข้ามเขตอำนาจ

## 7. สิ่งที่ต้องพูดตรง ๆ กับนักลงทุน

- **ดาวอังคารไม่ใช่ตลาด compute** ในอีก 10 ปี — มันเป็น demo ของสถาปัตยกรรมที่ทน latency ได้
  (และเป็นเรื่องเล่าที่ขายได้) แต่รายได้มาจาก Earth ก่อน
- **public network ทำให้ margin ลด** และเพิ่มภาระตรวจสอบ — ต้องคิดค่า redundancy ในราคาตั้งแต่ต้น
- **ความหน่วงคือเพดานทางฟิสิกส์** ไม่มี software layer ไหนเอาชนะได้ — ออกแบบให้งานอยู่ใกล้ข้อมูลเสมอ
