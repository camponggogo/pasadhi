# มูลค่าการแชร์คิดตามน้ำหนัก impact (%)

**ฉบับแก้ไขโมเดล · 2026-10-22** · โค้ด: `pasadhi/app/impact.py` · ข้อมูล: `bench/results/resource_impact.json`

> **สรุปสั้น:** เปลี่ยนจากการจ่าย "เหมาราคาต่อ core-ชั่วโมง" มาเป็น **แบ่ง pool ตามน้ำหนัก impact ที่วัดได้**
> ผลคือ CPU ได้เกือบทั้งหมด, RAM/Disk/Net ได้เศษเสี้ยว (เพราะไม่ได้อยู่บนเส้นทางวิกฤต) และ GPU ได้ 42 % เมื่อมี

---

## 1. สูตร

```
ค่าตอบแทนต่อชั่วโมง = pool × Σ (share_i × weight_i) + GPU_part

pool       = 2.50 บาท/ชม. × (threads ÷ 4)        ← เครื่อง 4 threads เต็มร้อย = 2.50 พอดี
weight_i   = น้ำหนัก impact ที่วัดได้ (ผลรวม = 1.0)
share_i    = % ที่ผู้ใช้ตั้งให้ทรัพยากรนั้น
GPU_part   = 3.00 บาท/ชม. × (VRAM ÷ 2GB) × share_gpu
```

## 2. น้ำหนักที่ใช้ (วัดจริง)

| โปรไฟล์ | CPU | GPU | RAM | Disk | Net |
|---|---:|---:|---:|---:|---:|
| `small_jobs` (ไม่มี GPU) | **98.0 %** | 0 | 0.4 % | 1.0 % | 0.6 % |
| `with_gpu` (มี GTX 1050) | 56.6 % | **42.2 %** | 0.2 % | 0.6 % | 0.4 % |
| `large_jobs` (สมมติฐาน) | 55.0 % | 0 | **30.0 %** | 10.0 % | 5.0 % |

สองโปรไฟล์แรกมาจากการวัด (fig06) · `large_jobs` เป็นสมมติฐานสำหรับงานที่ RAM เป็นตัวจำกัดขนาดงาน

## 3. ตัวอย่างการจ่ายจริง (เครื่อง 8 threads)

| ตั้งค่า | weighted | บาท/ชม. | บาท/เดือน |
|---|---:|---:|---:|
| CPU 20 / RAM 10 / Disk 5 / Net 10 | 11.4 % | 0.57 | 411 |
| CPU 35 / RAM 20 / Disk 10 / Net 20 | 20.0 % | 1.00 | 720 |
| CPU 90 / RAM 40 / Disk 20 / Net 40 | 93.5 %* | 4.44 | 3,197 |

\* โปรไฟล์ `small_jobs`; ถ้าเป็นการ์ดจอ GTX 1050 ที่ GPU 100 % ด้วย → 5.57 บาท/ชม. (4,007 บาท/เดือน)

**สังเกต:** RAM 40 % ให้เงินเพียง 0.004 บาท/ชม. — ตรงตามที่วัดว่า RAM ไม่ได้เพิ่ม throughput
(แต่มันกำหนด *ขนาดงานที่รับได้* ซึ่งควรจ่ายเป็น "โบนัสงานใหญ่" แยกต่างหาก — ดู §6)

## 4. ผลต่อ Group (150 เครื่อง) — ตัวเลขเปลี่ยนมาก

| โหมด | เดิม (เหมาราคา 0.55/thread-ชม.) | **ใหม่ (ตาม impact)** |
|---|---:|---:|
| Internal | −฿149,745 | −฿149,745 |
| Shared (30 %) | +฿175,032 | **+฿53,460** |
| Hybrid (30 %, reserve 5 %) | −฿3,885 | **−฿105,195** |

**ข้อสรุปที่ต้องยอมรับ:** ที่ส่วนแบ่ง 30 % การแชร์ **ไม่พอจ่ายค่าบริการ** อีกต่อไป
ตัวเลขเดิมสูงเกินเพราะคิด thread-hours ซ้ำกับ pool

### จุดคุ้มทุน (subscription ฿998/เครื่อง/เดือน)

| share | รายได้/เครื่อง/เดือน | คุ้มทุนหรือไม่ |
|---:|---:|---|
| 20 % | ฿163 | ไม่ |
| 30 % | ฿356 | ไม่ |
| 50 % | ฿843 | เกือบ |
| **60 %** | **~฿1,100** | **คุ้มทุน** |
| 70 % | ฿1,456 | คุ้ม + เหลือ |
| 90 % | ฿2,186 | คุ้มมาก |

**ทางเลือกเชิงธุรกิจ 3 ทาง:**
1. ลด subscription กลุ่มเหลือ **฿350/เครื่อง/เดือน** → 30 % ก็คุ้มทุน (แต่ margin หาย)
2. ขายเป็น "แชร์ 60 % แลกใช้ฟรี" — ขายง่ายและตัวเลขชัด
3. เพิ่มมูลค่า credit (เช่น 1.5×) เฉพาะงานที่ตรงกับความต้องการของเครือข่าย (ราคา dynamic)

## 5. ทำไมวิธีนี้ยุติธรรมกว่า

- ผู้ที่ให้ **CPU** (ตัวที่ทำให้งานเสร็จจริง) ได้เงินเกือบทั้งหมด — ตรงกับฟิสิกส์
- ผู้ที่ให้ **RAM/Disk ว่าง** ได้เล็กน้อย แต่ยังได้ *สิทธิ์รับงานใหญ่* (ซึ่งมีค่ามากกว่าเงิน)
- เครื่องมี **GPU** ได้ 42 % ของ pool — สูงกว่า CPU ต่อเครื่องอย่างมีนัยสำคัญ
- ไม่มีใครได้เงินจากการเปิดเครื่องทิ้งไว้เฉย ๆ เพราะค่าน้ำหนักมาจาก throughput ไม่ใช่ uptime

## 6. ข้อเสนอถัดไป (ต้องทดลอง)

- **โบนัสงานใหญ่:** ถ้างานใช้ RAM > 50 % ของที่ให้ → จ่ายเพิ่ม 1.5× (เพราะ RAM gate ขนาดงาน)
- **ราคา dynamic ตามคิว:** ถ้าคิว CPU ยาว → weight CPU เพิ่มชั่วคราว
- **น้ำหนักต่อกลุ่ม:** วัด utilisation จริง 2 สัปดาห์แล้วปรับ `PROFILES` ให้ตรงลูกค้า

## 7. ข้อจำกัด

- น้ำหนักมาจากเครื่องเดียว (i7-8550U) — เครื่องเซิร์ฟเวอร์จริงอาจให้น้ำหนัก RAM สูงกว่านี้
- `large_jobs` เป็นสมมติฐาน ยังไม่ได้วัด
- pool 2.50 บาท/ชม. อิงจาก credit rate ในโมเดลธุรกิจ ไม่ใช่ราคาตลาดที่ทดสอบแล้ว
