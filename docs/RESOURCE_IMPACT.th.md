## 1. ฮาร์ดแวร์ที่วัด

| รายการ | ค่า |
|---|---|
| CPU | Intel Core i7-8550U · 4 cores / 8 threads · 1.8 GHz base (15 W TDP) |
| RAM | 15.9 GB |
| GPU | AMD Radeon 530 2 GB (ไม่รองรับ CUDA) · Intel UHD 620 |
| Disk (write) | 74.6 MB/s (sequential, fsync) |
| Disk (read) | 1,138.6 MB/s (page cache) · random 4K **42,400 IOPS** |
| Network | loopback 12–524 MB/s ตามขนาด payload |
| OS | Windows 11 · uptime 88 ชม. |

## 2. CPU — ทรัพยากรที่impact สูงสุด

รัน GEMM 512² ในหน้าต่าง 100 ms แบบ duty cycle (วิธีเดียวกับที่แอปบังคับใช้):

| CPU share | GFLOP/s | หมายเหตุ |
|---:|---:|---|
| 10 % | 3.76 | ใช้งานเบา แทบไม่รู้สึก |
| 25 % | 7.65 | |
| 50 % | 25.37 | |
| 75 % | 33.29 | |
| **90 %** | **48.72** | **จุดสูงสุด** |
| 100 % | 32.35 | **ช้ากว่า 90 %** เพราะ thermal throttling (TDP 15 W) |

**Elasticity ที่ 35 %:** +10 point → **+48.1 %** throughput (ฐาน 14.7 GFLOP/s)

> บทเรียน: แล็ปท็อปคลาส U ตั้ง 100 % ได้ผลแย่กว่า 90 % — แอปจึงควรแนะนำเพดาน 90 % และปล่อยช่วงพักสั้น ๆ

## 3. RAM — ไม่ได้ทำให้เร็วขึ้น แต่กำหนดงานที่รับได้

| Working set | n (เมทริกซ์จัตุรัส) | GFLOP/s |
|---:|---:|---:|
| 16 MB | 1,448 | 90.9 |
| 64 MB | 2,896 | 98.1 |
| 256 MB | 5,792 | 94.9 |
| 512 MB | 8,192 | 92.3 |
| 1,024 MB | 11,585 | 94.7 |

Throughput แทบไม่เปลี่ยน (BLAS blocking ทำงานดี) → **RAM ไม่ใช่ตัวเพิ่มความเร็ว** แต่เป็น **เพดานขนาดงาน**:
ให้ RAM 20 % ของ 16 GB = 3.2 GB → รับงานได้ถึง ~n 20,000 (int8) หรือโมเดล ~1.5B แบบ int8

## 4. Disk — กระทบเฉพาะ "cold start"

- อ่านแคช 1 GB ใช้ **0.9 วินาที** (page cache) · เขียน 74.6 MB/s
- random 4K 42k IOPS → โหลดบล็อกโมเดลเล็ก ๆ ได้เร็ว
- ผลต่อ throughput ระหว่างรัน: **≈ 0** (งานอยู่ใน RAM หลังโหลด)

## 5. Network — กำหนด "คิวงาน" ไม่ใช่ความเร็วคำนวณ

| Payload | Throughput | jobs/s |
|---:|---:|---:|
| 1 KB | 12.0 MB/s | **12,327** |
| 64 KB | 524.1 MB/s | 8,386 |
| 1 MB | 321.7 MB/s | **322** |

งานของ PASADHI ~0.5–25 req/s → **network ไม่ใช่คอขวด** จนกว่าจะส่ง tile ใหญ่ (>64 MB) หรือ shard ข้ามเครื่อง

## 6. GPU — ถ้ามี จะพลิกน้ำหนักทั้งกระดาน

GTX 1050 (สเปก): 1.86 TFLOPS f32 = **22.4×** ของโหนด CPU นี้ (83.3 GFLOP/s)
ถ้าใส่การ์ดเข้าไปในเครื่องเดียวกัน → GPU กลายเป็น 42 % ของ impact ทันที (ดูตาราง §7)

## 7. สรุปน้ำหนัก impact (% ของทั้งหมด)

| ทรัพยากร | เครื่องนี้ (ไม่มี NVIDIA) | ถ้ามี GTX 1050 |
|---|---:|---:|
| **CPU** | **98.0 %** | 56.6 % |
| **GPU** | 0 % | **42.2 %** |
| RAM | 0.4 % | 0.2 % |
| Disk | 1.0 % | 0.6 % |
| Network | 0.6 % | 0.4 % |

![fig06](bench/results/fig06_resource_impact.png)

**วิธีคิดน้ำหนัก:** ใช้อนุพันธ์ของ throughput ต่อ 1 point ของแต่ละทรัพยากร ณ ค่าตั้งต้น (CPU 35 %, RAM 20 %,
Disk 10 %, Net 20 %) แล้ว normalize เป็น 100 % — ค่า CPU มาจากการวัดตรง, GPU มาจากสเปก, RAM/Disk/Net
มาจากผลวัดข้างต้น (ใกล้ศูนย์เพราะไม่อยู่บนเส้นทางวิกฤต)

## 8. คำแนะนำการตั้งค่า (จากตัวเลข)

| สถานการณ์ | ตั้งอย่างไร | เพราะ |
|---|---|---|
| เครื่องทำงานปกติของพนักงาน | CPU 20–35 %, RAM 10 %, Disk 5 %, Net 10 % | throughput ยังโตเป็นเส้นตรง และไม่รู้สึกหน่วง |
| เครื่องที่เปิดทิ้งไว้ 24 ชม. | CPU 75–90 %, RAM 20 % | ใกล้จุดสูงสุดแต่ยังเลี้ยง turbo |
| เครื่องมี GPU | GPU 60–80 %, CPU 30 % | GPU คือ 42 % ของ impact |
| งาน batch ใหญ่ | RAM 40–50 % | กำหนดขนาดงานที่รับได้ ไม่ใช่ความเร็ว |
| หลีกเลี่ยง | CPU 100 % | ช้ากว่า 90 % บน CPU คลาส U |

## 9. ข้อจำกัดของการวัดนี้

- เครื่องเดียว, แล็ปท็อป 15 W → ตัวเลข thermal throttling จะต่างบนเดสก์ท็อปหรือเซิร์ฟเวอร์
- Loopback network สูงกว่าสายจริงมาก (1 GbE จริง ≈ 118 MB/s) — ใช้เฉพาะดู shape ของกราฟ
- Disk read 1.1 GB/s เป็น page cache; อ่านครั้งแรกจะใกล้ค่า write (74.6 MB/s)
- GPU เป็นการ์ดจำลองจากสเปก ไม่ได้รันจริงบนเครื่องนี้
